# 无认证数据采集端点分析execution-framework

> 当遇到一个 API 端点对任意输入均返回 `{"result":"Success"}`（或等效成功响应）时，如何系统性地判断后端是否实际在处理数据，以及数据是否被持久化。
> 典型场景: Countly `/i`、Mixpanel、Amplitude、Firebase Analytics 等客户端 SDK 的数据采集端点。

---

## 问题本质

"任意参数返回 Success" 不等同于三个不同的东西：

```
① 请求被接收 → ② 数据被处理 → ③ 数据被持久化
```

只有①是可见的。②和③需要通过侧信道证据推断。本execution-framework的目标是用最少的请求最大化对②和③的认知。

---

## 一、请求解析深度验证（证明②存在）

### 1.1 JSON/请求体解析

这是最直接的证据：如果后端不解析请求体，所有 Content-Type 和所有 body 格式应返回一样的响应。

| 测试 | 期望结果（有解析层） | 期望结果（盲返回） |
|------|-------------------|-----------------|
| 合法 JSON `{"key":"val"}` | 200 Success | 200 Success |
| 畸形 JSON `{invalid}` | 400 或错误响应 | 200 Success |
| body 为 `null` | 400 或错误响应 | 200 Success |
| 空 body | 400 或错误响应 | 200 Success |

**判定**: 如果在合法 JSON 返回 Success 的同时，畸形 JSON 或 null body 返回不同的错误信息（400 或包含错误描述的 JSON），则**证明后端存在 JSON 解析层**，请求进入了处理管道。

### 1.2 Content-Type 过滤

| Content-Type | 期望结果（有过滤） | 期望结果（无过滤） |
|--------------|-----------------|-----------------|
| `application/json` | 200 Success | 200 Success |
| form-urlencoded | 200 Success | 200 Success |
| `text/plain` | 400 或拒绝 | 200 Success |
| `application/xml` | 400 或拒绝 | 200 Success |

**判定**: Content-Type 过滤是 Web 框架原始行为 vs 业务代码自定义行为的区分标志。
- `[Consumes]` attribute（ASP.NET Core）
- `@RequestBody` + MediaType（Spring Boot）
- Content-Type middleware（Go/Express）

无论哪种，都**证明请求在路由匹配后进入了指定处理器的代码路径**。

### 1.3 HTTP 方法分化

| 方法 | 期望结果（有路由限制） | 期望结果（无限制） |
|------|---------------------|-----------------|
| GET | 200 Success | 200 Success |
| POST | 200 Success | 200 Success |
| PUT | 405 Method Not Allowed | 200 Success |
| PATCH | 405 Method Not Allowed | 200 Success |
| DELETE | 405 Method Not Allowed | 200 Success |
| OPTIONS | 200（空或CORS头） | 200 |
| HEAD | 404 或 200 | 200 |

**判定**: HTTP 方法分化证明存在明确的路由定义——只有 GET/POST 被映射到处理逻辑，其他方法被框架层拒绝。这说明 `/i` 是设计上只接受写入请求的数据采集端点。

## 二、app_key 差分验证（证明app_key校验存在与否）

### 2.1 实验设计

控制变量: 请求方法、路径、参数结构、device_id 格式
自变量: app_key 的值

```
对照组A: 一个已从公共客户端确认的真实 app_key（若有）
对照组B: 一个格式相同但明确不存在的随机 app_key（必做）
```

如果无法确认真实 app_key，则所有候选 key 都属于 B。

### 2.2 对比维度

| 维度 | 有差异 → 含义 | 无差异 → 含义 |
|------|-------------|-------------|
| HTTP 状态码 | app_key 被同步校验 | app_key 在同步路径中未被校验 |
| 响应体 | app_key 被验证且不同处理 | 所有 key 在同一处理路径 |
| 服务端耗时 | 校验/查询耗时 | 路径无校验或校验代价一致 |
| 响应头 | 可能含错误追踪标识 | 无额外信息 |
| 幂等性 | 重复相同请求可能被拒绝 | 每次请求独立处理 |

### 2.3 结论规范

**不在报告中写**:
```
❌ 任意 app_key 均有效
```

**正确写法**:
```
✅ 公开响应无法区分合法 app_key 和无效 app_key，存在统一接收、异步校验或静默丢弃的可能。
```

## 三、服务器端处理假设（基于观测反推）

至少列举三种合理的后端实现解释，并为每种标注置信度。

### 典型假设集

```
假设A: 统一接收 → 消息队列 → 后台异步校验 → 合法:持久化 / 非法:丢弃
假设B: 统一接收 → 全部丢弃（请求完成基础日志后放弃）
假设C: 统一接收 → 全部持久化（无 app_key 校验）
```

### 置信度评估依据

| 证据 | 支持哪类假设 |
|------|-------------|
| K8s 多副本部署 | A > C > B（B 不需要多副本） |
| Content-Type 过滤 | A > C > B（B 不需要自定义 Middleware） |
| 健康检查端点 | A > C > B（生产级配置） |
| app_key 响应无差异 | A 或 B 均可解释，C 也成立 |
| 无读取端 | A 或 B（C 通常有读端供内部使用） |
| 响应无回执标识 | B > A > C |

## 四、持久化旁证收集（证明③存在与否）

### 4.1 可安全执行的旁证

- 检查响应体中是否存在 `event_id`、`queue_id`、`request_id` 等回执标识
- 检查响应头中是否存在 `Trace-ID`、`Span-ID` 等链路追踪标识
- 检查是否存在公开的 Dashboard 域名（但不尝试登录）
- 使用唯一测试标识（`security_research_<timestamp>_<random>`）写入后观察是否有任何可公开查询的统计变化

### 4.2 需要厂商协助的验证

- 检查生产接收日志是否包含测试事件
- 检查 app_key 校验记录
- 检查消息队列
- 检查数据库
- 检查 Countly / 分析后台 Dashboard

### 4.3 禁止执行的操作

- 批量发送事件
- 猜测读取端 Dashboard 路径
- SSRF 测试
- 路径穿越
- 越权访问管理端
- 管理 API Key 猜测
- 使用真实用户信息

## 五、证据闭环决策树

```
开始: 端点对所有输入返回 Success
├── JSON解析: 畸形JSON返回不同错误?
│   ├── YES → 存在解析层，请求进入处理管道
│   └── NO  → 可能是盲返回代理（仍不能排除，但证据弱）
├── Content-Type过滤: 400 vs 200?
│   ├── YES → 进一步证明存在业务代码处理路径
│   └── NO  → 过滤层的缺失不否定处理层的存在
├── app_key差分: 真实key vs 随机key有差异?
│   ├── YES → 存在同步校验
│   └── NO  → 无法区分（异步校验/统一处理/统一丢弃皆可能）
├── 持久化旁证: 有回执/追踪标识?
│   ├── YES → 数据大概率被持久化
│   └── NO  → 无法外部验证
└── 结论:
    ├── 清晰证明②④⑤ → 可交报告(中高)
    ├── 仅证明①②③   → 待确认/信息型
    └── 仅证明①      → 建议放弃
```

## 六、报告语言规范

### 禁止使用的表述

| ❌ 禁止 | 原因 |
|---------|------|
| "任意 app_key 均有效" | 无外部证据证明 app_key 在服务端被识别 |
| "已篡改生产数据" | 无法从外部确认数据是否进库 |
| "可无限伪造" | 未经速率限制测试 |
| "数据已被写入数据库" | 无读端回查入口 |
| "已影响统计/销售/业务指标" | 除非厂商确认 |
| "盲返回 Success" | 若已证明 JSON 解析和 Content-Type 过滤，则不是盲返回 |

### 推荐的语气

- **已证明**: "请求进入了解析处理流程"、"Content-Type 和 JSON 校验层存在"
- **推测**: "响应行为符合异步处理/静默丢弃/统一接收三种可能性"
- **未验证**: "无法从外部确认数据持久化"、"需厂商协助验证"
- **结论**: "基于当前可观测的公开响应，无法证明该端点存在违反预期行为的漏洞"
