## 九、SRC 证据收敛与报告定稿流程

**适用场景**: 发现多个漏洞线索后，提交 SRC 前必须执行的一轮系统化证据收敛。防止将攻击面线索、未经验证的推测和误报提交为漏洞。

**核心原则**: 所有结论严格区分为「已证明 / 高概率推断 / 尚未验证」，不得为提高评级而夸大影响。优先保证报告可信度、可复现性和对厂商审核友好。

**与正文「SRC 漏洞证据审计框架」的关系**: 审计框架对单个发现做逐项审计和对照测试；本流程是在其基础上的全局收敛——多个发现之间相互审视、降噪噪点、验证交叉证据，最终决定哪些送审、哪些放弃。

### 9.1 收敛物料清单

对每个发现，产出以下四个文件（按顺序递进收敛）：

```
1. evidence-matrix.md  ← 逐项证据审查（先做，确定每项发现的事实基础）
2. <发现>-report.md    ← 单个漏洞的完整审核报告（对确认的 GO 项产出）
3. <资产>-assessment.md ← 攻击面线索的技术评估（对 HOLD/NO-GO 项产出）
4. final-submission-plan.md ← 最终提交优先级排序（总收敛）
```

### 9.2 证据矩阵（Evidence Matrix）模板

对每个发现，填写以下字段：

| 维度 | 内容 |
|------|------|
| **已确认事实** | 只填写实际观测到的结果，不要包含推测。逐条列出。 |
| **未确认推测** | 明确列出需要但尚未获得的证据，以及它们支持的推论。 |
| **当前证据** | 原始请求、响应、屏幕截图等证物清单。 |
| **证据缺口** | 尚缺少的关键证据，以及为什么这些缺口重要。 |
| **可能评级** | 基于已有证据的保守评级。 |
| **是否建议提交** | GO / HOLD / NO-GO |
| **最容易被厂商打回的原因** | 从厂商视角出发，预判最可能的驳回理由。这条至关重要——如果自己都找不出驳回理由，说明提交标准不够严格。 |

### 9.3 噪声项快速降噪execution-framework

以下类型的发现大概率**不建议单独提交**（除非存在未认证敏感数据泄露、凭据泄露、调试信息泄露、跨租户访问或实际业务操作）：

| 发现类型 | 典型例子 | 降噪判断 |
|---------|---------|---------|
| **robots.txt 路径泄露** | Disallow 路径 | 被禁止的路径当前是否可访问？是否有内容？若无，放弃。 |
| **前端 JS 中的 API 地址** | 硬编码的 API URL | API 地址本身是否敏感？是否包含凭据？若无，放弃。 |
| **公开招聘数量接口** | 招聘系统 positionTotal | 招聘网站的公开职位数量一般为非敏感信息。 |
| **管理后台公网可达** | m-admin 域名 | WAF 是否拦截了所有请求？后端是否可到达？若无法到达后端，放弃。 |
| **返回 503 的 API 路由** | 503 Service Unavailable | 503 不构成安全缺陷，服务不可用不等于存在可利用入口。 |
| **标准 404 的路径** | — | 404 无内容时，放弃。 |

### 9.4 单个漏洞报告模板

对确认提交的漏洞，报告必须包含以下章节：

```
# <精确漏洞标题>

> 版本: v1.0
> 测试日期: YYYY-MM-DD
> 测试范围: <域名>（<SRC>授权资产）
> 报告类型: 安全漏洞报告
